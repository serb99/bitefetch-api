# BiteFetch – schema notes

Companion to [docs/design/database/schema.dbml](../database/schema.dbml), which is the single source of truth for the schema, and [docs/design/database/constraints.sql](../database/constraints.sql). Behaviour is defined in [order-state-machine.md](order-state-machine.md). Tags:
- *(decided)*: your decisions for this task, or R1–R13 / D1–D3 from the review.
- *(assumed Sn)*: my choice where the design was silent; listed in [§4](#4-assumed-decisions--veto-any) for you to veto.

**Verified on 2026-10-08** against a throwaway PostgreSQL 18 cluster:
- `schema.dbml` → `dbml2sql` (the `@dbml/core` exporter) → `constraints.sql`, run twice: no errors; 29 tables, 110 indexes (excluding partitions), 22 triggers, 62 CHECKs (all from constraints.sql §13), 47 foreign keys, `order_status_history` partitioned by month. Validated with both the DBML 2.x parser and the current one (no `checks` or `Project` blocks).
- 26 behaviour checks all passed. Highlights:
  - an order can't skip states (`pending_payment → delivered`) or go backwards (`picked_up → ready_for_pickup`)
  - nobody can cancel after `delivered`
  - capture before delivery is rejected
  - a second pending offer for an order is rejected
  - the same courier twice in one round is rejected
  - a duplicate idempotency key is rejected
  - a second open incident of the same type is rejected
  - a second live support chat is rejected
  - an availability override for another brand's item is rejected
  - an owned restaurant without opening hours is rejected
  - a full happy-path order writes 5 history rows with the correct actors

## 1. Conventions

| Topic | Rule |
|---|---|
| Keys | `bigint GENERATED BY DEFAULT AS IDENTITY` (what dbml2sql emits for `[pk, increment]`). Natural keys only where they are the identity: `stripe_events.event_id`, `platform_settings.key`, `route_cache.cache_key`. UUID only for `refresh_tokens.family_id` and `messages.client_msg_id` (client-generated). |
| Public ids | `orders.order_code` (`BF-XXXXX`) is shown to people; numeric `id`s stay internal *(decided R11)*. |
| Time | `timestamptz` everywhere; every deadline is compared with the database's `now()`. |
| Money | `integer` minor units (bani), `*_minor` columns plus `currency char(3) DEFAULT 'RON'` *(decided R1; naming assumed S1)*. `integer` holds up to 21.4 million RON per order, which is plenty. |
| Enums | Postgres enums with **lowercase** values *(assumed S2)*. The docs' `PENDING_PAYMENT` is `pending_payment` here. Adding a value later uses `ALTER TYPE … ADD VALUE` (no table rewrite). |
| Optimistic locking | `version int` on `users`, `applications`, `restaurants`, `orders`, `order_cancel_requests`. The application increments it in every `UPDATE` (docs: `version = version + 1`). |
| Audit | `SET LOCAL app.actor` / `app.reason` in every state-changing transaction; triggers copy them into `order_status_history` and `account_status_history`. |
| Errors | Triggers and CHECKs raise SQLSTATE `23514` (check_violation) and uniques `23505`. The API maps both to **409**. |

### Fixes to your draft (groups 1 and 2)

| Draft | Change | Why |
|---|---|---|
| `Enum x { a b c }` on one line | One value per line | DBML syntax; the one-line form doesn't parse |
| One-to-one refs with `-` (`ref: - users.id`) | Written as `child > parent` | dbml2sql put those FKs on the wrong table: `users.id` referenced `courier_profiles`, so no user could be inserted |
| `users`: no verification timestamp, no reason | Added `email_verified_at`, `status_reason` | A2/A3 and the admin UI's suspension and rejection reason |
| `courier_profiles.offline_reason varchar` | Enum `courier_offline_reason` (`manual`, `missed_offers`, `no_position`, `suspended`), plus CHECK online ⇔ no reason | Flow 3 Q2, R10 |
| `applications` had no `role`, no `version` | Added `role`, `version`, `updated_at`; CHECKs (constraints.sql §13) for attempts 1–3, decided ⇔ `decided_at`, reject reason required | A5/A6 use a version check; the role decides what approval creates |
| `email_tokens` couldn't express "older ones invalidated" | Added `revoked_at` | N7 resend |
| `refresh_tokens` couldn't chain rotations | Added `replaced_by_id` | Reuse detection and debugging |
| `account_status_history.actor_id bigint` | `actor varchar(64)` | `app.actor` is `'admin:42'` or `'system:sweeper'`; system actors have no user id |
| `brands`, `restaurants` lacked timestamps / version | Added `created_at`, `updated_at`, `restaurants.version`, `osm_synced_at`; CHECKs on coordinates | Admin unpause needs a version |

## 5. Partitioning

| Table | When | Key | Consequences |
|---|---|---|---|
| `order_status_history` | **Now** | `PARTITION BY RANGE (at)`, monthly | PK becomes `(id, at)`. Its FK *to* `orders` works (Postgres 12+). Nothing references it, so the composite PK costs nothing. Old months are dropped with `DETACH` + `DROP` (instant, no vacuum). `ensure_monthly_partitions()` keeps 3 months ahead, with a `DEFAULT` partition as a safety net. |
| `order_offers` | **Later**, only if it passes ~50M rows | — | Every unique index on a partitioned table must contain the partition key. "One pending offer per courier" across **all** orders can't then be global (a courier could hold pending offers in two monthly partitions at the month boundary). At ~9M rows/year, batched `DELETE` is enough (S5). |
| `messages` | Later (~50M rows) | `created_at` monthly | `UNIQUE (conversation_id, seq)` would need the partition key; switch to partitioning by `conversation_id` hash instead if needed. |
| `outbox`, `stripe_events` | Never | — | Short retention; plain deletes and eager autovacuum (§7) suffice. |
| `orders`, `order_items` | Not planned | — | Referenced by many FKs; the hot set is served by partial indexes. |

## 6. Nearest courier: plain lat/lng or PostGIS?

**Recommendation: plain `lat`/`lng` with a bounding-box filter now; PostGIS (or Redis GEO as a cache) when needed.**

- **Why it's enough now:**
  - The candidate set is only **online** couriers with a fresh position (flow 3 Q3), typically hundreds.
  - The query filters a box around the restaurant (±0.09° lat ≈ 10 km), then orders the few remaining rows by haversine distance in SQL.
  - Indexes: `courier_positions (lat, lng)`, `courier_positions (received_at)` and `courier_profiles (user_id) WHERE availability = 'online'`.
  - No extension to install, and B-tree updates are cheaper than GiST at one position write per courier every 3 s.
- **When to switch:**
  - more than a few thousand online couriers in one city, or
  - polygon delivery zones, or
  - the dispatch query's p95 above ~20 ms.
- **How to switch:**
  1. Add `geog geography(Point, 4326) GENERATED ALWAYS AS (ST_SetSRID(ST_MakePoint(lng, lat), 4326)::geography) STORED` to `courier_positions` and `restaurants`.
  2. Create `GIST (geog)` indexes.
  3. Use `ST_DWithin(geog, :restaurant, 3000 | 6000 | 10000)` with `ORDER BY geog <-> :restaurant LIMIT 5`.
  4. The lat/lng columns stay, so nothing else changes.

```sql
-- current query (S2), radius step r_km = 3 / 6 / 10
SELECT p.courier_id
  FROM courier_positions p
  JOIN courier_profiles cp ON cp.user_id = p.courier_id AND cp.availability = 'online'
 WHERE p.received_at > now() - interval '30 seconds'
   AND p.lat BETWEEN :lat - :r_km / 111.0 AND :lat + :r_km / 111.0
   AND p.lng BETWEEN :lng - :r_km / (111.0 * cos(radians(:lat))) AND :lng + :r_km / (111.0 * cos(radians(:lat)))
   AND NOT EXISTS (SELECT 1 FROM orders o WHERE o.courier_id = p.courier_id
                     AND o.status IN ('accepted','ready_for_pickup','picked_up'))
   AND NOT EXISTS (SELECT 1 FROM order_offers f WHERE f.courier_id = p.courier_id AND f.status = 'pending')
   AND NOT EXISTS (SELECT 1 FROM order_offers f WHERE f.order_id = :order_id AND f.round = :round
                     AND f.courier_id = p.courier_id)
 ORDER BY 2 * 6371000 * asin(sqrt(power(sin(radians(p.lat - :lat) / 2), 2)
        + cos(radians(:lat)) * cos(radians(p.lat)) * power(sin(radians(p.lng - :lng) / 2), 2)))
 LIMIT 5;
```

- **Batch it:** `UPDATE … WHERE id BETWEEN` in batches of ~5k, so long locks never block the API.
- **Constraints in two steps:** add them `NOT VALID` first, then `VALIDATE` in a separate migration.
- **Keep reads working:** keep the old column until the code no longer reads it (expand → migrate → contract).
